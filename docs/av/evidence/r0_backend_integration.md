Steps to add `room_mode`: (1) add a branch to `definitions.instruction.oneOf` in routes/scheduler/schedule.schema.json.j2 (oneOf starts at line 79; throw_event at 719-801 is the template), with `action: {const: 'room_mode'}`, a `mode` enum and `additionalProperties: false`. Running schedules can already trigger it through event triggers. The live schedules have event triggers such as `sleep`, `wake`, `Standby`, `sync` and `Generate`.
-> IMPLICATION: Wiring scheduler → room service is about 4 small edits plus a schema entry. It is low risk if the handler does not block. There is no generic `http`/`webhook` action today, so the room service cannot be called from a schedule without this code.

## 6. How does Alexa work, and how could 'disco mode' be added by voice?
[high] Alexa reaches Flask through ngrok at `POST /api/alexa` (app.py:116-132; VITE_PROD_PROPOSAL.md:30). There is no signature or applicationId verification. `process()` (routes/alexa.py:317-941) maps the Echo deviceId to the closest screen and then works in two stages. Stage 1 matches the Alexa intent name (alexa.py:474-519): repeat, schedule, select_refiner, cancel, undo, redo, set, animate, trigger, adapt, combine, load_schedule, unload_schedule, sleep, and a default that uses alexa-triage. The utterance is a free-text `utterance` slot. Stage 2 calls OpenAI with a system prompt and has a 7 s timeout (alexa.py:522-562). The model returns one of the intents in routes/data/marvin.schema.json.j2:9: respond_only, generate_image, other_action, change_refiner, animate, set_variable, trigger, adapt, combine, undo, redo, load_schedule, unload_schedule. Those are executed at alexa.py:570-937. The Alexa interaction model (intent names and sample utterances) is not in the repo; it lives in the Amazon developer console. Option A needs no Alexa code: put an event trigger `disco` (with a description) in the active schedule(s) whose instruction block calls the new `room_mode` action. 'trigger disco mode' then becomes the `trigger` intent → the LLM picks event_key from AVAILABLE_EVENTS → `throw_event` (alexa.py:610-634). Limits of option A: AVAILABLE_EVENTS is only built when a closest screen is known (alexa.py:375,424). It only lists event triggers in the top-of-stack schedule for that screen, its groups and global (alexa.py:247-315). The handler sleeps 2.5 s in the request thread before throwing (alexa.py:628), and the result is LLM-mediated. Option B is deterministic: add `case 'room':` (or 'disco') to the stage-1 match at alexa.py:474 and call the room service directly with a ~1 s timeout and a fixed mode enum, plus a matching intent in the Alexa console. Option C: add `room_mode` to the marvin schema enum and a stage-2 branch. That leaves an LLM choosing modes, which runs against the spirit of spec §11.
-> IMPLICATION: Option B is the right fit: deterministic, fast and mode-enum only. It still needs the Alexa console change, and it is unauthenticated over ngrok until P3's ingress plus T5 signature verification land. Voice control of lights through an endpoint with no verification breaks spec §12 'prevent untrusted guests'.

## 7. Can a separate process reuse Siren (utils/alerts), and what goes wrong if it does?
[high] It is importable without app.py: `from utils.alerts import alert, init_alerting`. `alert()` lazy-imports dispatcher and taxonomy (utils/alerts/__init__.py:22-64), and `python -m utils.alerts.selftest` already runs standalone (selftest.py:19-53). Requirements: the repo root on sys.path (dispatcher.py:33 and health.py:13 do `import config`), `requests`, and env loaded by the caller with python-dotenv; the package does not call load_dotenv itself. Use `init_alerting(None)` for the excepthook and worker without the Flask handler. It only installs `threading.excepthook`, so asyncio task exceptions need `loop.set_exception_handler`. Problems when two processes run it: (1) State file shared. `ALERT_STATE_PATH` is a config.py constant (config.py:39), not an env var, so both processes load and atomically replace logs/alerts_state.json (state.py:78-98; dispatcher.py:130-136). Last writer wins, which loses dedup state and confuses `last_alive` restart detection. (2) Dead-man ping masked. With `HEALTHCHECK_PING_URL` in its env, the second process pings healthchecks.io gated on its own health (dispatcher.py:383-402). In that process `ws_ok()` is True because no WS thread is registered (health.py:72-75) and there are no scheduler loops (health.py:51-69), so it would keep the dead-man check green while Flask is dead. (3) The once-a-minute sentinel lazily imports `routes.scheduler` (dispatcher.py:368-380 → health.py:55), which pulls screen-machine's whole routes import graph (openai, samsung, publisher…) into the room service. (4) Storm cap is per process: 12 emails/h each (config.py:45; dispatcher.py:277-281). (5) The email subject prefix is hard-coded `[screen-machine]` (dispatcher.py:414-415), and the log tail comes from logs/screen_machine.log (dispatcher.py:515-528), Flask's log, not the room service's. (6) Unknown categories default to severity 'error' (taxonomy.py:37-40). There is no HTTP endpoint for other processes to raise alerts into Flask's Siren; I looked and found none.
-> IMPLICATION: Plan a small, behaviour-neutral Siren refactor before a second process uses it. It should read the state path, subject prefix, log path and ping URL from env or settings, and replace the hard `routes.scheduler` import with a registered health-probe hook. Until then the room service must run with HEALTHCHECK_PING_URL unset and a separate state path, set by monkeypatching `config.ALERT_STATE_PATH` before the first alert. Gmail credentials can be shared: same four env keys.

## SURPRISES
- Reusing Siren unchanged in a second process would hide Flask's death. If HEALTHCHECK_PING_URL is set there, that process keeps pinging healthchecks.io: with no WS thread or scheduler loops registered it counts itself healthy (utils/alerts/health.py:72-85; dispatcher.py:383-402). Both processes would also overwrite logs/alerts_state.json, because the path is a config.py constant, not env (config.py:39). The once-a-minute sentinel imports routes.scheduler into the room service (dispatcher.py:368-380 → health.py:55).
- start.sh stops Flask with `pkill -f "python.*app\.py"` (start.sh:105). A room service started as `python room_service/app.py` would be killed by every Flask restart.
- /api/alexa has no Alexa request-signature or applicationId check and is publicly reachable through ngrok (start.sh:98; app.py:116-132). Adding voice room modes there would let anyone who knows the URL drive the lights and Sonos. That conflicts with AV spec §12, and the refactor plan defers signature verification to T5 (REFACTOR_PLAN.md:844).
- Refactor-plan principle 7 is 'No login, no kiosk or operator tokens' (REFACTOR_PLAN.md:61,292). The AV spec requires authenticated state-changing endpoints that keep guests out. The only auth that exists is the single ADMIN_API_TOKEN bearer check (routes/admin_api.py:18-36).
- Samsung TV pairing tokens sit in the git-tracked src/data/publish-destinations.json (fields `samsung-token`). The spec says pairing secrets must stay outside source control.
- The 8765 WS server relays any client's JSON to every kiosk and operator UI (overlay_ws_server.py:171-177,246-257), stripping only html/substitutions and generation_update. That makes it a usable status bus today, but it is unauthenticated and spoofable, and the refactor plan closes 8765 after P4.
- The mask on/off and brightness-override endpoints that a show mode needs to freeze the light-sensor mask exist, but their state is in-memory only (routes/display.py:42-104) and is lost on any Flask restart.
- Deadman probes only the public-IP hairpin URL (deadman.py:190-192). P3's plan to close WAN forwards will break it unless PROBE_URL moves to a LAN address. It also reads only fixed /api/health keys, so it ignores any new room key until deadman.py is edited.
- WSL already runs systemd as PID 1, with docker and containerd active, so systemd units and containers (e.g. MediaMTX) are available now. Yet nothing in screen-machine uses systemd, and /home/gjbm2/wsl-autostart.sh still restores the old dev topology (Vite dev plus `npx serve`) after a reboot.
- bd's live stream lab server runs on 0.0.0.0:8081 from a session scratchpad venv (`.../scratchpad/venv-enc`), not the repo .venv and not under the repo's experiments/ path. Nothing in the repo deploys the stream service yet.
- Alexa only offers voice events from the top-of-stack schedule of the closest screen and its groups, and only when a closest screen is known (routes/alexa.py:247-315,375,424). A 'disco' event trigger would vanish whenever someone loads a different schedule script.
- requirements.txt does not match .venv: python-dotenv is missing from it, samsungtvws is commented out but used, and websockets is listed twice. None of the AV protocol libraries are installed: OSC, Sonos, Hue, Art-Net, DTLS.
