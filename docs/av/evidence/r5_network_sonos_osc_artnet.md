# Networking and device-control facts: WSL2 inbound UDP, Sonos local control, OSC from Python, and the Art-Net protocol and Python receivers

## 1. Is netsh interface portproxy TCP-only? What is the current WSL networking state on this workstation?
[high] Yes, portproxy is TCP-only. The Microsoft netsh reference says, for every portproxy add/set/delete variant: "`protocol` - The protocol to use. Only `tcp` is supported." The WSL networking page also documents portproxy only for TCP. On this host, run read-only from the Linux side: `wslinfo --networking-mode` returns `nat`, `wslinfo --wsl-version` returns `2.4.12`, and the kernel is 5.15.167.4-microsoft-standard-WSL2 (built Nov 2024). The Windows edition and build were not checked, because the rules forbid touching Windows. The current rules are all TCP: 8080->5000, 5000, 8765 and 2222->22 in fix-wsl-networking.ps1:91-104, plus manual 8081 and 3001 rules (docs/KIOSK_INFRASTRUCTURE_NOTES.md:45-48).
-> IMPLICATION: Art-Net from Maestro (UDP 6454 inbound) cannot reach a WSL service the way traffic reaches it today. The programme needs an explicit 'UDP ingress' work item, decided before Phase 2 (the Art-Net proof).

## 2. WSL2 mirrored networking: Windows requirement, settings, inbound LAN UDP, Hyper-V firewall configuration
[medium] Requirement: Windows 11 22H2 or later. The wsl-config page marks networkingMode, firewall and dnsTunneling with footnote 2, "Require Windows 11 version 22H2 or higher". Enable it with `[wsl2] networkingMode=mirrored`. Related settings: `firewall` (default true: Windows Firewall and Hyper-V rules filter WSL traffic), and `[experimental] hostAddressLoopback` and `ignoredPorts` (mirrored only). Microsoft's listed benefits include "Multicast support" and "Connect to WSL directly from your local area network (LAN)". Inbound traffic needs Hyper-V firewall configuration, using the WSL VMCreatorId {40E0AC32-46A5-438A-A0B2-2B479E8F2E90}. Either run `Set-NetFirewallHyperVVMSetting -Name '{40E0AC32-...}' -DefaultInboundAction Allow`, or add a per-port rule `New-NetFirewallHyperVRule ... -Direction Inbound -VMCreatorId '{40E0AC32-...}' -Protocol TCP -LocalPorts 80`. The docs show only a TCP example; changing it to `-Protocol UDP -LocalPorts 6454` is the natural adaptation, but no doc shows it. The Hyper-V firewall is on by default on Win11 22H2 with WSL 2.0.9 or later. Inbound unicast UDP is not covered explicitly anywhere official. Community evidence is mixed. In Discussion #10614, inbound multicast UDP only worked after `DefaultInboundAction Allow` or `firewall=false` (accepted answer Aug 2025); one Jul 2026 report also needed `AllowHostPolicyMerge False`. Issue #10535 says inbound LAN traffic needed both Windows and Hyper-V rules. Issue #12065 reports inbound UDP replies dropped in mirrored mode with Docker IPvlan; a bot closed it unresolved.
-> IMPLICATION: Mirrored mode is the only built-in way to get LAN UDP into WSL, but it is not proven on this host and depends on the Windows build (unknown). Treat it as a spike with a pass/fail test: Maestro or a test sender unicasts to 192.168.1.205:6454 and a WSL socket receives it. Don't assume it works.
Sources: https://learn.microsoft.com/en-us/windows/wsl/networking; https://learn.microsoft.com/en-us/windows/wsl/wsl-config; https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/hyper-v-firewall; https://github.com/microsoft/WSL/discussions/10614; https://github.com/microsoft/WSL/issues/10535; https://github.com/microsoft/WSL/issues/12065

## 3. How would mirrored mode interact with the existing netsh portproxy rules and with Linux services binding ports that are already proxied? What are the known issues?
[medium] The wsl-config entry for `ignoredPorts` says it "Specifies which ports Linux applications can bind to, even if that port is used in Windows... so those applications are not blocked even when that port is used for other purposes on Windows". So by default, in mirrored mode a Linux bind is blocked when Windows holds the port. Each portproxy rule is a Windows listener (IP Helper on 0.0.0.0:<port>). So 5000, 8080, 8765, 2222, 8081 and 3001 would collide with Flask, the overlay WebSocket and the lab ports; this is my inference from the doc. Their connectaddress (the old 172.x NAT IP) would also no longer exist. Mirrored mode has no port translation: WAN:8000 -> Windows:8080 -> WSL:5000 and 2222->22 would stop working unless the router forward changes or Linux also listens on 8080. sshd on 22 would clash with any Windows OpenSSH server. The fix-wsl-networking.ps1 boot task (REFACTOR_PLAN.md:447) would have to be retired. Other known issues: the Windows host reaching WSL by its LAN IP needs `hostAddressLoopback=true` (Microsoft staff in issue #11034); IPv6 ::1 localhost is not supported; Microsoft's Sept 2023 known issue was "Address already in use" errors for dev containers; and issue #10683 reports Docker ports unreachable from the host. Changing the mode needs `wsl --shutdown`, which stops the production Flask app.
-> IMPLICATION: Switching to mirrored is a production network migration, not a toggle. It means deleting all portproxy rules, changing the router forward(s), adding Hyper-V firewall rules per port (TCP and UDP 6454), retiring the boot script and taking an outage. It belongs in or after refactor plan P3 (network reach), with a rollback path (networkingMode=nat plus the script).
Sources: https://learn.microsoft.com/en-us/windows/wsl/wsl-config; https://github.com/microsoft/WSL/issues/11034; https://github.com/microsoft/WSL/issues/10683; https://devblogs.microsoft.com/commandline/windows-subsystem-for-linux-september-2023-update/; https://wsl.dev/technical-documentation/localhost/; /home/gjbm2/dev/screen-machine/fix-wsl-networking.ps1:91-104; /home/gjbm2/dev/screen-machine/docs/REFACTOR_PLAN.md:447

## 4. Multicast, mDNS and SSDP support (NAT vs mirrored)
[medium] NAT mode: multicast does not cross the WSL NAT. This is established in the context notes, and a third-party write-up says the WSL2 NAT drops cross-host mDNS (224.0.0.251:5353). Mirrored mode: Microsoft documents "Multicast support", but users report that inbound multicast only arrives after the Hyper-V firewall default inbound is set to Allow (or firewall=false). Some report it still fails, and bridged mode was their only fix. Bridged mode is "marked as deprecated since WSL 2.4.5" (wsl-config).
-> IMPLICATION: Don't design anything that depends on multicast discovery (Sonos SSDP, Hue mDNS, Art-Net broadcasts) reaching WSL. Use DHCP reservations and configured IPs for Maestro, the Hue bridge and the Sonos players.
Sources: https://learn.microsoft.com/en-us/windows/wsl/networking; https://github.com/microsoft/WSL/discussions/10614; https://learn.microsoft.com/en-us/windows/wsl/wsl-config

## 5. What are the alternatives for inbound UDP into NAT-mode WSL2? Is there any built-in option?
[medium] I found no built-in Windows client feature that forwards UDP into WSL NAT. portproxy is TCP-only. NetNat `Add-NetNatStaticMapping` acts on WinNAT instances, while WSL's NAT is reported to be HNS/ICS with an empty `Get-NetNat`; that is unverified, so treat it as not available. The options are: (a) A Windows-side user-space UDP relay that listens on 0.0.0.0:6454 and sends to <WSL IP>:6454. It needs a Windows Firewall inbound UDP rule (scoped to Maestro's IP), a boot-time scheduled task and a WSL-IP refresh like fix-wsl-networking.ps1. Its latency should be well under a millisecond (inference), and WSL sees the relay as the source, not Maestro. (b) WSLRouter, a pcap/Npcap packet redirector. Its README calls it experimental; it has 2 stars, needs source edits, and warns that WinNAT causes duplicate packets. Not recommended. (c) Bridged mode, deprecated since WSL 2.4.5. (d) The newer `consomme` networking mode exists, but nothing documents it accepting inbound LAN traffic; not found. (e) Receive Art-Net on a native Linux host (the kiosk mini-PC or a small Pi) and forward state over TCP/WebSocket through the existing TCP portproxy. (f) Run the Art-Net receiver natively on Windows.
-> IMPLICATION: The lowest-risk near-term path is (a): a small Windows-side UDP relay, managed like the portproxy script, so the Art-Net proof isn't blocked on a mirrored-mode migration. Mirrored mode can then be evaluated as the long-term fix in P3. Option (e) on the kiosk conflicts with refactor plan principle 11 (nothing on the kiosk should depend on the sensor being there).
Sources: https://learn.microsoft.com/en-us/windows-server/networking/technologies/netsh/netsh-interface-portproxy; https://github.com/ttsuki/WSLRouter; https://learn.microsoft.com/en-us/powershell/module/netnat/add-netnatstaticmapping; https://learn.microsoft.com/en-us/windows/wsl/wsl-config

## 6. Is Sonos local UPnP/SOAP control still available on S2 firmware in 2026, after the 2024 app rewrite?
[high] Yes, but it is now a user-toggleable legacy feature. Sonos player 85.0-66270 (July 2025, app 80.23 or later) added Account > Privacy & Security > Connection Security with three settings. UPnP is ON by default; Sonos says it controls "the older UPnP protocol", which is no longer actively maintained, and turning it off may break older apps and third-party controllers. Authentication is OFF by default; when on, third-party integrations that use Sonos cloud services and LAN APIs must authenticate. Guest access is ON by default. Sonos security advisory SSA-2025-0002 (2025-08-25, High) recommends that S2 users set UPnP to Off because of a LAN-side token-leak issue, which is fixed in S2 v17.1.1 (85.0-66270). Home Assistant states "UPnP must be enabled on your Sonos system for this integration to work"; if it is off, setup fails with 403 from DeviceProperties/Control. HA's dev branch still pins soco==0.31.5 and sonos-websocket==0.2.0, and is iot_class local_push. SoCo releases in Sept/Oct 2026 add new hardware (Beam Ultra, Amp Multi), which indicates UPnP control still works on current firmware.
-> IMPLICATION: Phase 0 must record the household's UPnP, Authentication and Guest access settings. If the owner followed the advisory and turned UPnP off, SoCo control fails. Keep the sonos-adapter thin and swappable, because Sonos is deprecating UPnP gradually.
Sources: https://en.community.sonos.com/product-updates/a-new-player-update-is-live-6930092/index3.html; https://www.sonos.com/en-gb/security-advisory-2025-0002; https://www.home-assistant.io/integrations/sonos/; https://raw.githubusercontent.com/home-assistant/core/dev/homeassistant/components/sonos/manifest.json; https://community.openhab.org/t/sonos-after-change-to-new-api/144106

## 7. SoCo status: release, maintenance, play/pause/volume/group control, events (GENA) vs polling, and SSDP discovery when IPs are static
[high] SoCo 0.31.5 was released 2026-10-06; releases 0.31.0-0.31.5 run from Apr to Oct 2026. It requires Python 3.6 or later (WSL has 3.12.3), has 1.6k stars and 68 open issues, and its last commit is 2026-10-06. It controls transport, volume and grouping over UPnP on port 1400; playback commands go to the group coordinator. Events are UPnP GENA and need an inbound HTTP callback. The listener defaults to port 1400 (config.EVENT_LISTENER_PORT) and "will attempt to listen on the next available port, within a range of 100" if that port is busy (events.py:170-200). The advertised IP is found by a UDP connect to the speaker (events_base.py:768-787), which inside WSL NAT returns the 172.x eth0 address that speakers cannot reach. Set `config.EVENT_ADVERTISE_IP='192.168.1.205'` (honoured at events_base.py:417-418), pin the listener port, add a TCP portproxy 1400->WSL:1400 (TCP, so portproxy works), and add a Windows firewall rule scoped to the Sonos IPs. An asyncio events module (events_asyncio.py) exists. Polling (e.g. transport info every 1-2 s) needs no inbound path; Home Assistant falls back to polling when callbacks fail. Discovery: soco.discover() uses SSDP multicast 239.255.255.250:1900, which won't work from WSL NAT. With static or reserved IPs it isn't needed: use soco.SoCo('<ip>'), or scan_network(networks_to_scan=['192.168.1.0/24']), which probes TCP 1400.
-> IMPLICATION: Use SoCo in-process in the room service. For the spec's 'observed state, not last button press', either add a TCP 1400 portproxy rule with EVENT_ADVERTISE_IP (cheap, since TCP works), or poll at 1-2 s for v1. Always resolve the coordinator from zone-group topology, because users regroup speakers in the Sonos app.
Sources: https://pypi.org/pypi/soco/json; https://github.com/SoCo/SoCo/releases; https://raw.githubusercontent.com/SoCo/SoCo/master/soco/config.py; https://raw.githubusercontent.com/SoCo/SoCo/master/soco/events.py; https://raw.githubusercontent.com/SoCo/SoCo/master/soco/events_base.py; https://raw.githubusercontent.com/SoCo/SoCo/master/soco/discovery.py; https://www.home-assistant.io/integrations/sonos/

## 12. What is the ArtDmx packet layout and what are the ports?
[high] Source: Art-Net 4 Protocol Release V1.4, Document Revision 1.4dp, 23/10/2025, pp.62-64. Fields in order: ID[8] = "Art-Net\0"; OpCode Int16 OpOutput/OpDmx 0x5000, "Transmitted low byte first" (bytes 0x00 0x50); ProtVerHi (0) and ProtVerLo ("Current value 14"); Sequence ("incremented in the range 0x01 to 0xff... set to 0x00 to disable"); Physical (input port, used for merge discrimination); SubUni ("low byte of the 15 bit Port-Address", i.e. Sub-Net<<4 | Universe); Net ("top 7 bits of the 15 bit Port-Address"); LengthHi/LengthLo (big-endian; "should be an even number in the range 2-512"); Data[Length] starting at byte offset 18, so the maximum datagram is 530 bytes. Port-Address is 15 bits (Net, Sub-Net, Universe; 32,768 addresses). Art-Net uses UDP 0x1936 (6454) "as both source and destination". Other OpCodes: OpPoll 0x2000, OpPollReply 0x2100, OpSync 0x5200.
-> IMPLICATION: A receiver is about 50 lines. Validate ID, OpCode and ProtVer >= 14, decode the Port-Address, and honour Length. Maestro has a toggle for universe 0 vs 1 numbering, so expect an off-by-one when patching.
Sources: https://art-net.org.uk/downloads/art-net.pdf (Art-Net 4 V1.4 rev 1.4dp, pp.9-10, 13, 62-64)

## 13. Art-Net 4 unicast vs broadcast rules, ArtPoll/ArtPollReply discovery, and refresh rate
[high] ArtDmx: "Unicast Transmit Yes. Broadcast No." Also: "ArtDmx packets must be unicast to subscribers of the specific universe... The transmitting device must regularly ArtPoll the network... If there are no subscribers to a universe, the controller shall not send ArtDmx. There are no conditions in which broadcast is allowed." ArtPoll goes to the directed broadcast address: "all controllers broadcast an ArtPoll every 2.5 to 3 seconds", controllers may assume a 3 s maximum wait for replies, and limited broadcast 255.255.255.255 "should not" be used. ArtPollReply is unicast only, sent after a random delay of up to 1 s, with a minimum valid length of 207 bytes. ArtSync is directed broadcast only. Refresh: "For a gateway outputting DMX512, this will always be the maximum rate of 44Hz"; non-DMX gateways may declare more. An input that is active but unchanged re-transmits about every 4 s, with 800-1000 ms recommended. MaestroDMX lets you either "scan for available nodes" or type the IP manually, and 'Add Node' sends to several IPs. Its Art-Net article doesn't say whether it is strict about subscriptions, or its packet rate.
-> IMPLICATION: Configure Maestro's Art-Net node manually as unicast to 192.168.1.205. Phase 2 must check whether Maestro keeps sending when the receiver never answers ArtPoll. In NAT mode the directed-broadcast ArtPoll never reaches WSL, so a Windows relay may also need to answer ArtPoll. Set the stale threshold above the keep-alive interval (seconds, not the 30 ms in the spec's example) until Maestro's real cadence is measured.
Sources: https://art-net.org.uk/downloads/art-net.pdf (pp.10, 16-18, 25, 62-66); https://maestrodmx.freshdesk.com/support/solutions/articles/153000252041-art-net-and-maestrodmx

## 14. Which Python libraries can receive Art-Net, and is a library better than a tiny parser?
[high] stupidArtnet 1.6.0 (2025-03-12, 99 stars, MIT) has StupidArtnetServer. It binds ''/6454 with SO_REUSEADDR in a raw `_thread` and does a blocking recvfrom(1024). It matches the exact 12-byte header (ProtVer 14 only), discards the sender address and ignores the Length field. Its sequence filter (`new_seq > old_seq or old_seq-new_seq > 0x80`) drops packets after a sender restart until the sequence catches up, up to about 127 packets (about 3 s at 44 Hz). It doesn't answer ArtPoll. pyartnet 2.0 (2025-11-04, GPL-3.0) is asyncio but send-only: its source has sendto paths and no receive path. It supports ArtNet, sACN, KiNet and synchronous multi-universe output. Apollon77/artnet-bridge (the AV spec's Hue candidate, Node) was pushed 2026-08-11 and has 3 stars and 16 open issues.
-> IMPLICATION: Write the receiver as a small asyncio DatagramProtocol inside the room service. It should validate packets, keep a latest-value store per Port-Address, and track source, sequence and arrival time so the spec's freshness check works, optionally sending ArtPollReply. Use pyartnet as a synthetic 'fake Maestro' transmitter, so the renderer and Hue mapping can be built and soak-tested before the DMX fixtures arrive.
Sources: https://raw.githubusercontent.com/cpvalente/stupidArtnet/master/stupidArtnet/StupidArtnetServer.py; https://pypi.org/pypi/stupidArtnet/json; https://raw.githubusercontent.com/spacemanspiff2007/PyArtNet/master/readme.md; https://github.com/spacemanspiff2007/PyArtNet/tree/master/src/pyartnet; https://api.github.com/repos/Apollon77/artnet-bridge

## SURPRISES
- REFACTOR_PLAN.md:1138 (D22) keeps netsh portproxy 'unless WHEP/UDP is chosen', as if UDP only matters for the WebRTC transport. The AV spec's Art-Net path from Maestro (UDP 6454 inbound) makes inbound UDP mandatory whatever transport is chosen. Neither document plans for it.
- Sonos's own security advisory SSA-2025-0002 (2025-08-25) recommends S2 users turn UPnP OFF. That breaks SoCo and Home Assistant style control (403 from DeviceProperties/Control). The AV spec's 'local UPnP/Sonos library' plan doesn't mention this toggle or the new Authentication and Guest access settings from July 2025.
- node-sonos-http-api, named in the AV spec, has had no tagged release since 2017. Its engines field excludes Node 23 and later, and it depends on SSDP multicast discovery, which doesn't cross WSL NAT.
- Art-Net 4 says a controller 'shall not send ArtDmx' to a universe with no ArtPoll-discovered subscriber, and broadcast is never allowed. If Maestro enforces this, a WSL receiver that can't see the directed-broadcast ArtPoll may get no data even with a UDP relay. The AV spec only says 'ensure unicast destination configuration'.
- The AV spec's example freshness 'artnetAgeMs: 30' assumes a continuous stream. Art-Net allows unchanged data to be re-sent only every ~0.8-4 s, so a naive stale timer could flap to the fallback look during static scenes.
- Mirrored networking would reverse refactor plan principle 7 (REFACTOR_PLAN.md:61: 'netsh makes every client look like the Windows host'). WSL would see real source IPs. All portproxy rules, the 8080->5000 and 2222->22 port translations and fix-wsl-networking.ps1 would have to go, and the router forward would change.
- WSL 'bridged' mode, which many guides suggest for UDP, has been deprecated since WSL 2.4.5. This host runs WSL 2.4.12 in NAT mode.
- Sonos events (GENA) need an inbound TCP callback, and SoCo's auto-detected callback IP inside WSL would be the unreachable 172.x address. Neither document mentions the extra portproxy rule (TCP 1400) and the EVENT_ADVERTISE_IP setting this needs.
- Apollon77/artnet-bridge, the AV spec's preferred Hue path, has 3 GitHub stars and 16 open issues, and is itself an Art-Net receiver, so it hits the same inbound-UDP problem.
