## 7. P4b Light-reactive mask Tier 1: verdict for the AV programme
[medium] Verdict: re-scope to be mode-aware and lower its priority (3–4 d → 3.5–4.5 d). It can follow the AV core but cannot be dropped, because it is an explicit owner requirement for gallery mode. The conflict: the Yoctopuce sensor is USB-attached to the mini-PC that drives the Frames, so it is probably in the same room as the Hue lights and future moving heads (inference). compute_mask maps lux to brightness and also to colour temperature (routes/display_utils.py:173-203). Show lighting (Hue fades, beams, mirror-ball spots) easily moves lux by more than the 0.75 EV snap threshold for 2 samples, which is 100 ms at 20 Hz. The faster filter would therefore make the screens pump with the show. The mask's brightness (z 5) and warm-multiply (z 6) layers sit above the LiveLayer (z 2), so they would also tint the colours Maestro assigns to the screen fixtures. P4b's acceptance tests an optical loop only against the TVs, not against Hue or the heads. What the AV programme needs: (1) a new policy.mask_source value ('frozen'/'show'). In Ambient/Piano/Disco/Intro the mask is identity, or frozen at its pre-show value, and dimming comes from the fixture DIMMER, applied in the renderer. (2) A slow ramp back when gallery mode resumes. (3) Hue-step and beam-sweep tests added to the acceptance. (4) Optionally, lux published to the room service as an input.
-> IMPLICATION: Without mode-awareness, P4b would actively degrade shows. Add a show-mode mask policy to the screen contract before the first show.
Sources: docs/REFACTOR_PLAN.md:329-357; docs/REFACTOR_PLAN.md:343; docs/REFACTOR_PLAN.md:269; docs/REFACTOR_PLAN.md:906-935; routes/display_utils.py:173-203; src/pages/DisplayPage/hooks/useMask.ts:4

## 19. Which §2 principles conflict with the AV spec or need revisiting?
[medium] P5 'three planes' (control/media/files): the AV adds a fourth, the show/lighting plane. It is UDP Art-Net in at ~40 Hz, latest-value, lossy and freshness-gated (stale → safe look), with no ordering, snapshot or rev semantics, plus a rate-limited device-command plane (Hue/OSC/Sonos out). It needs its own principle. P6 'fail to still, never to black': in shows, black can be legitimate (Maestro DIMMER=0, /triggers/blackout), and the spec's failure response is 'fade to configured safe look'. Revise to 'fail to the mode's safe look (gallery: still); commanded darkness is rendered, not a failure'. P7 'security from network reach; no login, no kiosk/operator tokens' conflicts directly with spec §12 ('authenticate state-changing web endpoints; prevent untrusted guests from controlling lighting/Sonos'). In a home where guests join the Wi-Fi, LAN reach equals guest reach. Source-IP checks stay useless under NAT portproxy, so the options are router guest isolation or app auth (for example a household pairing token, in the same spirit as the existing ADMIN_API_TOKEN exception). Unauthenticated lighting control is also a photosensitivity/safety exposure. P8 'single owner for every mutable thing' needs extending to physical devices: Hue has two owners (house app/automations and the show), so the supervisor needs explicit hand-over (snapshot → Entertainment stream or REST takeover → restore). P10 critical-path rule: the list of legacy touches must grow (show-mode policy in DisplayPage, mask freeze, overlay suppression, a room claim owner, Samsung TV fixes). P11 'one page, dumb host, sensor remote' is compatible and reinforced (fixed kiosk URLs). It rules out the spec's implied separate MediaMTX reader pages: WHEP would have to be an inline driver. P12 'local degrade, server upgrade' is compatible. P4 (stream_service imports only schema/) should be applied unchanged to room_service.
-> IMPLICATION: Amend §2 before AV design work: add a show-plane principle, a device-ownership/hand-over rule and a physical-safety rule, and re-decide P7 for room control (guest isolation or token).
Sources: docs/REFACTOR_PLAN.md:53-69; AV_SPEC.md §12 (lines 477-485); AV_SPEC.md §12 failure matrix (lines 455-466); media-server/remote-scripts/kiosk-loop.sh:30-31

## 20. Which §7 'explicitly not doing' items conflict or need revisiting?
[medium] 'No microservice split beyond the stream service' (§1 line 49, §7 line 1151) conflicts. The AV programme needs a separate always-on room service (Art-Net receiver, show-state, Hue/OSC/Sonos/TV adapters, supervisor, room UI/API) for isolation: physical-lighting-adjacent behaviour must not depend on a Flask process that hosts blocking schedulers. The spec itself says to split 'for isolation/performance reasons'. Revise to 'stream service + room service (+ renderer if host-native)'. 'No app auth, login, RBAC, kiosk or operator tokens' conflicts with spec §12 (see principle 7). 'No Docker' is compatible if systemd is chosen; the spec allows 'systemd/Docker Compose', and MediaMTX is a single binary. 'No ASGI/FastAPI migration' applies to the legacy app only; the room service can be aiohttp like the lab and stream service. Appendix A removes fastapi/uvicorn from the shared requirements, so a FastAPI room service needs its own requirements file. 'No NATS/Redis' is compatible: the show-state bus can be in-process in the room service, with a local WS/UDP feed to the renderer. 'No Chrome or NVIDIA driver upgrades' may need revisiting if the renderer or encoder choice needs driver ≥570 (PyAV, on-demand IDR for fast join, D21). Chrome 136 cannot receive HEVC over WebRTC on Linux in any case (MediaMTX docs). 'No server-side GStreamer playout' and 'no media on :8765/waitress' are compatible.
-> IMPLICATION: Two §7 items (microservices, app auth) must be explicitly overturned for the room. The rest stand.

## 21. Which §6 decisions (D1–D27) need revisiting because of the AV spec?
[medium] D22 WSL networking: its trigger has fired. The plan says 'netsh unless WHEP/UDP is chosen', and Art-Net needs inbound UDP whatever the transport choice; Sonos events and discovery need inbound TCP/multicast. Options: (a) mirrored networking, which needs Windows 11 22H2+, Hyper-V firewall rules and `wsl --shutdown` (a prod outage, so do it after P2's units). It also exposes real source IPs, which changes P7's premise. (b) A Windows-native UDP relay to the WSL IP. (c) Run the Art-Net receiver/renderer natively on Windows (TouchDesigner is Windows/macOS only). (d) Host the room service on a separate small always-on Linux box, for example the spare N95 in D27 item 14, which also decouples Hue/Sonos/OSC control from workstation reboots. D10/D11 transport and codec: the spec mandates H.264 over WebRTC via MediaMTX and 'test 1080p60 first'. The plan picks ws-fMP4-MSE with HEVC 4K30 because of the owner's quality priority. Per MediaMTX's docs, Chrome reads H.265 over WebRTC only on Windows, so WebRTC on the Linux kiosk forces H.264, which on Chrome VA-API needs the SPS fix (WebRTC-path behaviour untested). WebRTC also needs UDP 8189 into WSL, or an ICE-TCP fallback (webrtcLocalTCPAddress) that portproxy could carry. Recommendation: keep HEVC 4K30 and treat the latency class per mode (gallery live = quality/MSE; show = interactive, with wctrack as the candidate); test WHEP only as an alternative. D12 arbitration: add a room/show owner, probably above scheduler and below operator; needs a decision. D13: reinforced. The 18:00/22:00 reloads must go before evening shows. D14/D25: add a show-mode mask policy (freeze/identity). D15 inline only: compatible; any WHEP/WebRTC player must be an inline driver. D16: extend to a full port plan (room-service HTTP, 6454/udp, OSC, MediaMTX if used). D24 Game Mode: it cannot be switched per mode (no network API), so one setting must serve both gallery art (Movie, accuracy) and show latency. Game Mode saves about 25–35 ms through the One Connect box and coincided with 4K60 appearing on 2026-10-13. ## 24. Which AV spec claims or assumptions does the refactor plan's evidence contradict or qualify?
[medium] (1) 'H.264 over WebRTC; test 1080p60 first, then 1440p60 or 4K' conflicts with three things: the owner's recorded priority (4K quality over ultra-low latency); D11 (4K30 HEVC primary); and the on-device evidence that HEVC 4K30 already runs at 157 ms (MSE) or 76 ms (wctrack) p50 pre-TV. ## SURPRISES
- CONTEXT_NOTES says kiosk-loop.sh relaunches Chrome 'on HDMI hotplug or Chrome death'. In code it relaunches only when the HDMI connector set changes (kiosk-loop.sh:97 and :161; webview-manager.sh behaves the same). Nothing respawns a dead Chrome, and the comment at routes/admin_api.py:158 wrongly claims a webview manager does. This matters for the spec's failure matrix ('watchdog restores failed kiosk').
- The docs disagree on display mode. REFACTOR_PLAN §3.5 (lines 311, 317) and P3 step 5 say both TVs have run 3840x2160@60 since 2026-10-13, after the owner switched Game Mode ON. KIOSK_INFRASTRUCTURE_NOTES (status table line 18, §3, line 127 'Nothing has been changed on the TVs yet'), the lab README (line 27) and CONTEXT_NOTES all still say 4K@30. Not re-verified (no ssh allowed).
- The X-presentation fix is further along than the refactor plan says. The plan says bd is 'choosing between ZaphodHeads and a Wayland compositor (research in progress)', but the working tree already contains a ZaphodHeads implementation: media-server/remote-scripts/xorg/20-zaphod.conf and a per-screen branch in kiosk-loop.sh:77-117 (dated 2026-10-13 19:21). Its comments imply it was tested (a 3839x2159 window without a WM drops to ~50 fps). Whether it is deployed on the box is unknown.
- MediaMTX's own docs state that Chrome reads H.265 over WebRTC only on Windows with a capable GPU. The AV spec's WebRTC/MediaMTX transport therefore cannot carry HEVC to the Linux kiosk, which conflicts with D11 (4K30 HEVC) and with the owner's 4K-quality priority.
- D22 was written with only WHEP in mind as a UDP trigger. Art-Net (UDP 6454 inbound) fires that trigger regardless of transport, and so do Sonos UPnP event callbacks and SSDP discovery. netsh portproxy accepts only protocol=tcp, and WSL is in NAT mode (eth0 172.28.255.46/20).
- The deployed kiosk infrastructure is still uncommitted (KIOSK §7) and now has further uncommitted changes from today (ZaphodHeads), all in the tree prod runs from and that several agent sessions share.
- The AV spec assumes wired Gigabit Ethernet in the room. The owner's recorded statement is that a cable to the drawing room is impossible and powerline is the only option (KIOSK notes lines 9-11). The Art-Net and Hue bridge network paths in that room are therefore probably powerline or Wi-Fi, with unmeasured UDP loss.
- The refactor plan's light-response acceptance (optical loop check against the TVs only) does not consider room lighting. In the AV room, Hue and moving heads would drive the lux sensor, and compute_mask changes both brightness and colour temperature from lux (display_utils.py:173-203), so P4b's faster filter would pump the screens during shows.
- The 2026-10-13 on-device run gives no positive evidence for the spec's 'H.264 1080p60 first'. The H.264 4K 25M MSE row and the H.264 1080p60 wctrack row both presented 0 frames, though this is confounded by the undiagnosed session-change failure that zeroed every row after the first.
- The spec's candidate Apollon77/artnet-bridge is immature (3 stars, no releases, Node >= 22.13). Its dashboard defaults to :8080, the same port the Windows portproxy listens on for the production frontend.
