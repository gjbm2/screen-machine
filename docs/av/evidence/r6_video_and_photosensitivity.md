# Video pipeline and photosensitivity safety facts for two live 4K streams: WSL2 workstation (RTX 4060 + Quadro P4000, driver 566.14) to two Chrome 136 kiosks on an Intel N95 driving two Samsung Frame Pro TVs

## 1. Q1a. Can Chrome 136 receive HEVC (H.265) over WebRTC? Is a flag needed, and which version shipped it?
[high] Yes, and no flag is needed. Chromestatus feature 5153479456456704 ('H265 (HEVC) codec support in WebRTC') shipped enabled by default in M136 on desktop, Android and WebView. It is hardware-only: 'we will not provide a software implementation'. The Chrome 136.0.7103.113 source confirms this: media/webrtc/webrtc_features.cc:71-73 sets kWebRtcAllowH265Receive to FEATURE_ENABLED_BY_DEFAULT (Send at :64-66 is also on, but only where the platform has an HEVC encoder, which Linux lacks). Linux builds compile it in: webrtc.gni sets rtc_use_h265 = enable_hevc_parser_and_hw_decoder, and media/media_options.gni defines that as proprietary_codecs && (... || is_linux). rtc_video_decoder_factory.cc:144-184 offers H265 Main/Main10 in SDP only when the GPU factories report a hardware HEVC decoder, with no OS check. rtc_video_decoder_adapter.cc says 'HEVC does not have SW fallback'. In WebRTC M136 the receiver always uses the H26x packet buffer for H265 (video/rtp_video_stream_receiver2.cc:1190-1195), so the old pre-136 flags are obsolete: --enable-features=WebRtcAllowH265Receive and --force-fieldtrials=WebRTC-Video-H26xPacketBuffer. Caveat: MediaMTX's own v1.21.2 docs say Chrome reads H265 'only on Windows and only when a capable GPU is present'. The Chromium source contradicts that, but it has not been tested on the kiosk.
-> IMPLICATION: HEVC 4K over WebRTC is a real option for the kiosks, so the spec's 'H.264 WebRTC, 1080p60 first' is not forced by the browser. Make a 10-minute on-device check a gate before any WebRTC work: on the kiosk, RTCRtpReceiver.getCapabilities('video') must list video/H265, and chrome://media-internals must show VaapiVideoDecoder for a MediaMTX WHEP stream. If H265 is missing from the SDP, the call fails outright, because there is no software fallback.

## 2. Q1b. Does WebRTC decode use VA-API hardware decode on Linux by default, or does it need flags?
[high] It needs a flag, the same one MSE and WebCodecs need. In Chrome 136, media/base/media_switches.cc:706-716 has kAcceleratedVideoDecodeLinux ('AcceleratedVideoDecoder') on by default when built with VA-API, but kAcceleratedVideoDecodeLinuxGL off by default. media/mojo/services/gpu_mojo_media_client_linux.cc:109-117 then returns VideoDecoderType::kUnknown, meaning no hardware decoder, on the GL path unless AcceleratedVideoDecodeLinuxGL is enabled. The Vulkan path at :118-134 needs Vulkan, VulkanFromANGLE and DefaultANGLEVulkan instead. WebRTC's RTCVideoDecoderAdapter uses the same GPU factories, so this gate applies to it too. Chrome's other WebRTC rules: the adapter is hardware-only. H.264, VP8 and VP9 fall back to software below 320x240 (kMinResolution) or beyond kMaxDecoderInstances = 8; HEVC never falls back. The kiosk already runs --enable-features=AcceleratedVideoDecodeLinuxGL in one switch, with the iHD driver and the render group in place (kiosk-loop.sh:41-50; KIOSK notes §2). Hardware decode has been confirmed on the box for H.264 (WebCodecs) and for HEVC MSE, but not yet for WebRTC.
-> IMPLICATION: Hardware decode works only while the kiosk keeps the flag, the iHD driver and the render group. Keep all three in deploy scripts and in health checks; P1 should probe chrome://media-internals for VaapiVideoDecoder. Chrome is not apt-held, and a manual upgrade to 155 could change these gates, so hold Chrome at 136 or re-verify after any upgrade.

## 3. Q1c. How does MSE/WebCodecs HEVC hardware decode differ from WebRTC on this kiosk?
[high] Both depend on the same VA-API gate, and Linux Chrome has no software HEVC decoder in either path. MSE and WebCodecs HEVC are controlled by kPlatformHEVCDecoderSupport, on by default (media_switches.cc:317-319). Linux VA-API HEVC has existed since Chrome 108.0.5354.0 (StaZhu). Measured on the box on 2026-10-13: live HEVC 3840x2160@30 at 18 Mbit/s over MSE played on both TVs at once, with VA-API decoding and the video engine 9-16% busy. Dropped frames were 0.28% and 0.24% once each TV had its own X screen. Capture to on-screen p50 was ~126 ms (p95 127-143), of which ~67 ms is the 2-frame MSE target. An earlier wctrack run measured p50 76 ms. Practical differences: (1) MSE and WebCodecs ride a WebSocket (TCP), so they pass through netsh portproxy unchanged, while WebRTC needs UDP or ICE-TCP. (2) Low-delay MSE needs mvhd duration 0 and no mehd. WebCodecs needs a secure context. (3) H.264 from NVENC lacks the VUI bitstream_restriction field, so the lab rewrites the SPS for MSE and WebCodecs. WebRTC's own H.264 depacketizer already rewrites incoming SPS VUI (video_rtp_depacketizer_h264.cc:122-124 with Direction::kIncoming; sps_vui_rewriter.cc:376-407 forces max_num_reorder_frames 0). (4) WebRTC controls its own jitter buffer and pacing; MSE latency is set by the buffer target.
-> IMPLICATION: The measured ws-fMP4/MSE HEVC 4K30 path already meets the owner's quality-first priority on the real hardware. WebRTC would have to beat it on latency or robustness to justify the UDP/WSL networking work. Keep the transport abstraction (ws-fmp4-mse first, WHEP as an option), as in refactor plan D10.

## 4. Q2. Does MediaMTX support HEVC over WebRTC/WHEP to Chrome, and which transports does it offer? Is there a TCP ICE fallback?
[high] Yes on codecs. MediaMTX v1.21.2 (latest release, 2026-10-08) reads AV1, VP9, VP8, H265 and H264 video over WebRTC (docs/4-read/03-webrtc.md). The browser page is at http://host:8889/<path> and WHEP at http://host:8889/<path>/whep. The codec is negotiated from the browser's own offer (internal/servers/webrtc/reader.js). Its docs still warn that Chrome reads H265 'only on Windows', which conflicts with Chrome 136's source (Q1a). The docs list four connection methods (25-webrtc-specific-features.md:30-33):
1. A static UDP port, webrtcLocalUDPAddress, on by default at :8189.
2. A static TCP port, webrtcLocalTCPAddress, off by default. This is ICE-TCP and is the TCP fallback.
3. A random UDP port with STUN hole punching.
4. A TURN relay over TCP.
Any NAT must forward 8189 (UDP, or TCP when TCP is enabled). webrtcAdditionalHosts must list the server's LAN address. So TCP fallback exists natively. Inference: under WSL NAT with TCP-only netsh portproxy, the working options are webrtcLocalTCPAddress :8189 with portproxy for TCP 8189 and 8889 plus webrtcAdditionalHosts 192.168.1.205, WSL mirrored networking, or MediaMTX running natively on Windows. WebRTC over TCP brings back head-of-line blocking on loss, the same as ws-fMP4.
-> IMPLICATION: WHEP does not force mirrored networking (D22): ICE-TCP through portproxy is a cheap first experiment. The WSL-specific workarounds are inference, though, so test them before relying on them. Keep refactor plan principle 'no microservices beyond the stream service': if MediaMTX is adopted, it becomes the stream service's distribution layer rather than an extra component.

## 5. Q3a. RTX 4060 NVENC: how many engines, what concurrent-session limit, and can it run two 4K30 HEVC low-latency encodes?
[high] Engines: 1 NVENC (8th gen, Ada) and 1 NVDEC (5th gen) per NVIDIA's support matrix. Session limit: NVIDIA's NVENC Application Note for SDK 12.2 and 13.0 says 'On non-qualified GPUs, the number of concurrent encode sessions is limited to 8 per system', counted across all non-qualified cards together. An NVIDIA forum moderator quotes the requirement for that limit as Windows driver ≥551.76 or Linux ≥550.54.14. The SDK 13.1 note and the current support matrix now say 12 per system, but SDK 13.1 needs driver ≥610 and I found no driver version tied to the 12 limit. With 566.14 installed, assume 8. Throughput: NVIDIA's per-NVENC Ada HEVC figures at 1080p, 8-bit, CBR with low-latency tuning are P1 1055 fps, P3 494, P5 343 and P7 343. Scaling those by 4x for 4K (my assumption) gives ~264 / ~124 / ~86 fps. Two 4K30 streams need 60 4K frames per second: about 23% of the one engine at P1 (the lab's preset) and about 70% at P5 or P7. One session cannot exceed one engine, because Split Frame Encoding needs more than one NVENC. Lab measurements: capture to packet ~21-27 ms at 4K30, encode stage 11-14 ms, settings p1 / tune ull / CBR / -delay 0 / -bf 0 / 1 s GOP (lab/encoder.py:36,54-61). PyAV and FFmpeg 8 need NVENC API 13, which needs driver ≥570.
-> IMPLICATION: Two 4K30 HEVC encodes fit easily on the 4060, even at higher-quality presets. The session cap is shared per system, including any NVENC use on the Windows side such as OBS, ShadowPlay or browsers (inference from 'per system'), so the plan's 'configurable NVENC session cap per GPU' (REFACTOR_PLAN.md:288) should count per system. Both streams share one engine, so the second waits: from ~4 ms at P1 up to ~12 ms at P5 and above (inference). Splitting the streams across the two GPUs removes that wait.

## 9. Q5a. What do the photosensitive-epilepsy standards (ITU-R BT.1702-3, Ofcom/ITC, WCAG 2.3.1, Harding/IRIS) say in numbers?
[high] ITU-R BT.1702-3 (approved 22 Nov 2023, in force):
- A flash is a pair of opposing luminance changes of ≥20 cd/m² when the darker image is below 160 cd/m² (SDR and HDR).
- If the darker image is ≥160 cd/m² (HDR only), a flash is a Michelson contrast (Lhigh−Llow)/(Lhigh+Llow) above 1/17.
- Any transition to or from saturated red counts as potentially harmful, whatever the luminance.
- A sequence is not permitted when the concurrent flash area exceeds 25% of the displayed screen and there are more than 3 flashes (6 changes) in any one second.
- Flashes whose leading edges are ≥360 ms apart (50 Hz) or ≥334 ms apart (60 Hz) are always acceptable.
- Fast cuts count as flashes.
- A flashing sequence longer than 5 s 'might constitute a risk even when it complies'.
- Patterns (informative): more than 5 light/dark stripe pairs are a risk if stationary over 40% of the screen, or over 25% if they oscillate, flash or reverse. Smooth one-direction flow is exempt.
- Measurement assumes SDR peak white of 200 cd/m² and HLG of 1000 cd/m².
- Annex 4: receiver-side adaptive temporal filtering of 10-30 Hz stimuli, typically ≥20 dB reduction at ≥10 Hz.
- Annex 5: risk rises in a darker room, on a brighter or larger screen, and with a closer viewer; it advises a well-lit room and ≥2 m.

Ofcom: the legacy ITC note (2001) still hosted by Ofcom has the same numbers. Its separation rule is '9 frames or more' (at 25 fps).

WCAG 2.3.1 (Level A): no more than 3 general and/or 3 red flashes in any 1 s, OR a flash area of ≤0.006 sr within any 10° visual field (25% of that field). A general flash is a change of ≥10% of maximum relative luminance with the darker state below 0.80. A red flash (WCAG 2.2 working definition) is a transition involving R/(R+G+B) ≥ 0.8 with a CIE 1976 u'v' difference above 0.2. WCAG notes that large screens fill more of the visual field. 2.3.2 (AAA) drops the area exception.

Analysers: HardingFPA (commercial; tests to Ofcom, ITU, NAB-J and ISO) reports a risk trace with a 'Pass with Caution' warning zone. EA's IRIS (BSD-3-Clause, open source) fails more than 3 flashes per second, flags an 'extended failure' for 2-3 flashes per second sustained over 5 s, and warns above 2 flashes per second. Its transition thresholds are a relative-luminance accumulation of ±0.1 and a red accumulation of ±20.
-> IMPLICATION: A 'flash limiter' needs to sit in the renderer output (per-frame luminance and red analysis) and in the Hue and Maestro adapters, not only on physical strobes. IRIS is a ready reference implementation for both offline testing of recorded output and in-loop checking.
Sources: https://www.itu.int/rec/R-REC-BT.1702-3-202311-I/en; https://www.itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.1702-3-202311-I!!PDF-E.pdf (Annex 1 Guideline 1-2, Attachment 1, Annexes 2, 4, 5); https://www.ofcom.org.uk/__data/assets/pdf_file/0021/16248/gn_flash.pdf (ITC Guidance Note, July 2001); https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html; https://www.w3.org/TR/WCAG22/; https://www.hardingfpa.com/technical-support/how-to-interpret-hardingfpa-results/; https://github.com/electronicarts/IRIS (README; licence BSD-3-Clause)

## 10. Q5b. Which concrete numeric limits should the flash limiter enforce for screens and room lighting?
[medium] This combines the standards above; the synthesis is mine.

Screens:
- Treat as a flash any opposing pair of luminance changes ≥20 cd/m² with the darker image below 160 cd/m². This needs the Frames' measured nits per code value; if unknown, use a conservative ΔY ≥ 0.1 of relative luminance. Treat any transition to or from a red with R/(R+G+B) ≥ 0.8 as a flash.
- Hard cap: ≤3 flashes in any sliding 1 s window, enforced as ≥334 ms between flash leading edges.
- Apply the cap whatever the flashing area. WCAG's 10° visual field is much smaller than a 75-inch screen at room distance, which subtends roughly 31°x18° at 3 m by my calculation, so '25% of the screen' alone is not conservative.
- Warn above 2 flashes per second, and do not sustain 2-3 flashes per second for more than 5 s (IRIS extended failure; BT.1702 5 s note).
- Avoid more than 5 high-contrast stripe pairs that oscillate or reverse over 25% of the screen, or are stationary over 40%.
- Count hard cuts as flashes.
- Optionally low-pass luminance at 10-30 Hz (BT.1702 Annex 4).

Room lighting:
- No broadcast standard applies. The Epilepsy Society cites the UK HSE as recommending public-performance strobes 'at a maximum rate of four Hertz or less'. It gives 3-30 Hz as the common trigger range, sensitivity up to ~60 Hz in some people, and sensitivity below 3 Hz as uncommon.
- Recommended: cap Hue and moving-head flashes at the same ≤3 per second (stricter than HSE's 4 Hz), and disable or cap Maestro STROBE/SHUTTER effects.
- Screens and lights share the viewer's field of view, so count flashes from both sources together (inference).
- Provide a 'photosensitive-safe' room mode that is on by default.
-> IMPLICATION: Add a cross-cutting safety track early, before any music-reactive visuals or Hue Entertainment streaming reach the room. It needs:
- a shared flash budget in the show-state layer
- a limiter stage in the renderer output
- rate and transition limits in the Hue adapter
- a policy for the Maestro strobe and shutter attributes
- IRIS runs on captured screen output as an acceptance test

The Frames' brightness in the chosen picture mode must be measured to set the 20 cd/m² threshold properly.

## SURPRISES
- The lead notes say the TVs run 4K@30 and 'Game Mode OFF decided (D24)'. As of 2026-10-13 the owner has switched Game Mode ON and both TVs run 3840x2160@60, with the HDMI Forum block now in the EDIDs (KIOSK_INFRASTRUCTURE_NOTES.md:18,23,104-108; stream-latency README.md:27). The settings doc still recommends Game Mode Off.
- The lead notes say the two kiosk windows share one 7680x2160 X screen. That layout was measured as broken (no page flip, ~30 fps per TV, 31-34% dropped frames, tearing) and replaced the same day with one X screen per TV (xorg/20-zaphod.conf plus a modified kiosk-loop.sh:77-117). Both changes are uncommitted.
- The AV spec prefers H.264 over WebRTC and testing 1080p60 first. Chrome 136 receives HEVC over WebRTC by default (hardware-only, Linux compiled in), and the N95 already decodes two 4K30 HEVC streams at 9-16% video-engine load, so decode capacity does not justify the conservative start.
- MediaMTX's own v1.21.2 docs say Chrome reads H265 over WebRTC 'only on Windows', which contradicts the Chrome 136 source. One of them is wrong for this box; only an on-device test settles it.
- WebRTC's H.264 depacketizer already rewrites incoming SPS VUI (max_num_reorder_frames = 0). The NVENC H.264 'reorder depth' trap that the lab fixed by hand for MSE/WebCodecs would not occur over WebRTC.
- The refactor plan (D10/D22) assumes WHEP needs UDP into WSL and therefore mirrored networking. MediaMTX supports ICE-TCP on a static port, which netsh portproxy can carry.
- The GeForce NVENC session cap is 8 per system with drivers ≥551.76 (NVIDIA's current matrix and the SDK 13.1 note say 12), not the old 3 or 5. The cap is per system across all GeForce cards and is shared with Windows-side NVENC users. The Quadro P4000 is unrestricted but has only 1 NVENC per NVIDIA's matrix, despite its GP104 die.
- VA-API hardware decode is NOT on by default in Chrome 136 on Linux with GL; it depends on the AcceleratedVideoDecodeLinuxGL flag. Chrome is not apt-held, and an apt upgrade would install Chrome 155, which may change these gates.
- BT.1702-3 (2023) supersedes the frame-count rule in the Ofcom-hosted 2001 ITC note with 360 ms / 334 ms separations and adds an HDR rule (Michelson contrast 1/17). For a 75-inch screen at room distance, WCAG's 10° visual-field area rule is far stricter than '25% of the screen'.
