Lifecycle and cold-start budget for on-demand render workers
(written 18 Oct 2026 ~19:10; no screen live: GET 127.0.0.1:8702/api/sessions -> [] at 18:47 [M])

LIFECYCLE (design, [I])
- The control (today's stream_service on :8702, minus render/encode) stays up: it is light. With no screen live it uses
  0.84 s CPU per 10 s = 8.4% of a core [M 18:5x, /proc/1084303/stat]: main thread 7.3%, two executor threads 1.0% and 0.6%
  [M per-thread]. RSS 473 MB, 26 threads, two cuda-EvtHandlr threads (it holds CUDA contexts from --warm) [M].
- WorkerPool in the control, keyed by GPU index. One worker hosts one session (one GIL per screen).
  * POST /api/sessions: take an idle worker on that GPU, else spawn one at the start of the handler, in parallel with the
    first_scene pick and the anchor decode.
  * Session ends (DELETE / TTL / failed): worker stops the engine and frees GPU buffers (renderer.py:871-915), then lingers 30 s.
  * Linger expires: worker exits (its CUDA context goes with it). A new session on that GPU inside the linger reuses it.
  * A worker is never reused for two live sessions at once. A lingering worker can take any profile: RenderContext is per
    session (gpu.py:236-250, Engine.create_context renderer.py:228-231); only the CUDA context and compiled modules are per process.
- Library browsing: Previews keep one 720p session per tab and re-cue it with a hard cut (preview.py:1-15), TTL 30 s plus
  keepalive, GPU 1 preferred unless a TV is on it (preview.py:28, 68-81). So a tab holds one warm worker while it plays,
  and the next tab or card within 30 s reuses it.
- Room re-entry / fallback / retries create a new session for the same screen within seconds: the linger covers them.
- Crash: a worker that dies = engine on_failed -> session.error + failed (sessions.py:2304-2313): room's existing fallback path.
- Shutdown: the control ends sessions, then kills its workers (Linux: process group; Windows: a job object).
- Priority: WSL workers cannot raise themselves (rtprio 0, no sudo, init.scope RT budget 0: report section 7 [M there]);
  only nice others. A Windows-native worker can set ABOVE_NORMAL or HIGH priority class without elevation [I, Win32 rules; not tried].
- Spectre: the control keeps the stream card (scripts/ctl). WSL workers are children of it, not separate servers. Windows-native
  workers are a Windows-side piece: CLAUDE.md requires a Spectre card + scripts/windows/<thing>/*.ps1 + a docs/PORTS.md entry
  for any listener.

COLD-START COMPONENTS (WSL, CPU-only timings run with CUDA_VISIBLE_DEVICES="" and nice 19 on a loaded box)
1. Interpreter + worker imports
   - import cupy: 1.46 s, 1.16 s wall (user 1.64/1.39 s) [M 18:51]
   - import stream_service.renderer, .gpu, .encode.encoder + cupy: 1.13 s wall (user 1.64 s) [M 18:51]
   - import stream_service.server (control side; cupy not imported): 1.44 s wall; -X importtime: aiohttp 0.65 s of 1.53 s
     (importtime_server.txt) [M]. A worker that talks plain sockets does not need aiohttp.
2. Plug-in modules
   - Full Registry().discover(): 850 modules, 3.01 s wall, 4.2 s CPU under nice 19 (registry_discover_timing.txt) [M 18:51];
     1.12-1.17 s in production at service start (log 16:31:16, 16:49:54) [M]. cupy is not imported by discovery [M].
   - Lazy import of one GLSL plug-in module: p50 0.5 ms, max 27 ms (40 modules) [M 18:52] -> the worker imports only what it prepares.
   - An earlier run in this folder (discover_timing.txt, 17:10, lighter load; not written by me) measured: import server 0.72 s wall,
     discover 1.78 s, registry.catalog() 0.25 s -> 2.07 MB JSON, import cupy 0.69 s wall. So the import costs above swing ~2x with box load.
3. CUDA context + per-GPU warm (throwaway 1280x720 RenderContext, config transitions + cut/crossfade, live_art 2x4K pinned)
   - "GPU N warm in": GPU 0 (RTX 4060, desktop GPU) 0.4-4.8 s, GPU 1 (P4000) 0.2-1.9 s, 20 service starts 17-18 Oct [M log].
   - Not separately measured: bare context creation vs the transition loads. Not run here (CPU-only rule).
4. Kernel compile
   - GLSL -> CUDA translation is per process (lru_cache: plugins/_lib/glsl/runtime.py:70-78): p50 24 ms, p90 63 ms, max 130 ms
     per program; CUDA source p50 50 KB (glsl_translate_timing.txt) [M 18:52].
   - NVRTC: CuPy caches cubins on disk at ~/.cupy/kernel_cache: 3807 cubins, 168 MB, last write 17:10 [M]. A worker loads them
     from disk on a hit [U: cost not measured]; a miss compiles [U: seconds per large shader].
   - The cache key includes CUPY_CACHE_KEY (a build hash, here 87417f5d...), the NVRTC version and the arch
     (cupy/cuda/compiler.py:688-712) [M]. A Windows CuPy build very likely misses every WSL entry [I/U].
5. Session start in a warm process (session_start_times.txt) [M log 14-18 Oct]
   - starting -> ready (context-ready process: RenderContext, sound alloc, anchor + scene setup and prime, 6 pinned 12.4 MB
     slots, ffmpeg spawn + NVENC init, first IDR): 2160p p50 1.21 s, p90 3.07 s, max 5.70 s (n=156);
     720p p50 0.69 s, p90 1.13 s, max 3.25 s (n=234).
   - before that: 'first scene (auto)' pick line -> starting (anchor decode + Session()): p50 0.43 s, p90 0.79 s, max 1.80 s (n=28).
   - NVENC init blocks the first pipe writes for ~0.3 s (renderer.py:454-455 comment) [U].

ESTIMATE, cold worker to session.ready, 4K [I]
   typical  ~1.1-1.5 s imports + ~0.8-1.9 s context/warm + ~1.2 s session start  ~= 3-4.5 s
   worst    ~1.5 + 4.8 + 5.7                                                       ~= 12 s (both screens starting together on a busy box)
   warm reuse (inside the 30 s linger): like today, p50 1.2 s.
   Overlap that is free: spawn first, then pick + decode (0.4 s) in the control while the worker imports.
